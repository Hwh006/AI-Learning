# source 素材摘要页（IR 层）

## 一句话定位

source 页 = **raw 的编译中间表示**。它不是索引（下游真要拿材料），也不是原文搬运（要滤掉噪声）。

写得好不好，只看一条：

> **给定这一页 source + 编译规范，能不能重新产出所有引用它的页面层内容（concept / solution / comparison），而不需要回读 raw？**

这叫**编译封闭性**，是唯一完备性标准。字数、条数、篇幅都不构成标准。

**职责分工**：`index.md` 统一定义页型职责、适用条件和边界；本 Skill 定义本页型的字段、章节、执行步骤与校验。分类冲突按 `index.md` 处理，写作结构以本 Skill 为准，并同步修正不一致内容。

**标签自检**：写入或修改 Wiki 页时，按项目 `AGENTS.md` 的标签规则，从本页主旨、反复讨论的对象与关键机制提取具体检索词；每个主题标签须能在正文找到依据。素材类型标签另保留，不能单独充当主题标签。

| 本 skill 自带 | 什么时候看 |
|---|---|
| `scripts/verify_source_page.py` | 每写完一页必跑，见第 5 步 |

## 触发条件

用：

- 新素材进了 `raw/`，要建 source 页
- 已有 source 页要重跑或校验
- 下游页面（concept / solution）缺数值、缺原话、缺出处，要回补 source 层
- 用户问「这个数字哪来的」「原文原话怎么说」「这个断言有什么依据」

不用：

- 只是讨论、回答概念问题 → 不写页
- 要写 concept / solution / comparison → 那是页面层的事，source 只存「原文说了什么」
- 素材还在 `raw/` 没定要不要入库 → 先问用户，不要自动 ingest

## 输入契约

必填：

- **素材文件路径**：`raw/` 下的具体文件。用户只说主题时，先定位文件再动手，不要凭主题猜。
- **素材类别**：课程总结 / 课堂转写 / 智能纪要 / 面试资料 / 外部文章。决定 `material_type`、`reliability` 和位置标注格式。
  - **外部文章**（网页文章、官方工程博客、推文等一手公开文本）：`reliability` 取 `结构化原文`；位置标注用 `§标题路径`（如 `〔§Now: Design interfaces〕`、`〔§THEN AND NOW · 图 B 注〕`），开篇（H1 下、首个 `##` 之前）写 `〔§开篇〕`——这类材料通常没有编号章节，§编号格式用不上。
  - ⚠️ **英文素材两个坑**：① 原文用弯引号（`’` U+2019、`“”` U+201C/201D），摘录必须连引号一起照抄，写成 ASCII 直引号会**搜不到**；② `--candidates` 的漏摘提醒是中文词表（万/亿/条/次…），对英文几乎失效（实测 81 段只报 6 条，且多为元信息行），**必须人工通读全文**找数值、条件与反例。
- **工作目录**：项目根。本 skill 内的脚本路径（`skills/wiki-source-page/…`）、素材路径（`raw/…`）和输出路径（`wiki/sources/…`）都相对它，命令请在这个目录下执行。

## 执行流程

### 第 1 步 · 查重与分档

```bash
HASH=$(shasum -a 256 "raw/xxx.md" | cut -d' ' -f1)
grep -rl "$HASH" wiki/sources/ || echo "需要 ingest"
```

- 哈希命中 → 已 ingest 过，**不要重跑**（除非用户明确要求）
- 同一素材内容变了 → **重生成整页**，不是追加
- 同主题但换了新文件 → **新建**一页，旧的冻结不动
- 定 `reliability`：口语转写类必须标 `口语转写`，面试题标 `练习材料`

### 第 2 步 · 从下游反问（不要从原文开头顺着摘）

写之前先回答三个问题：

1. **这一页会被用来支撑哪些页面、哪些断言？**
2. **那些断言需要什么材料才站得住？**（数值？条件？案例？反例？）
3. **原文里这些材料在哪？**

跳过这一步的结果是摘到开场白。现有 40 页里 29 页的失败都出在这里。

### 第 3 步 · 定位与抽取

用脚本拿位置，**不要手数段号**：

```bash
# 列出原文里疑似含数值 / 硬约束 / 案例的段落，防止漏摘关键内容
python3 skills/wiki-source-page/scripts/verify_source_page.py \
  --raw "raw/record_cleaned_markdown/xxx.md" --candidates

# 给一段原话，返回可直接粘进页面的位置标注（段号 + 段首 10 字）
python3 skills/wiki-source-page/scripts/verify_source_page.py \
  --raw "raw/record_cleaned_markdown/xxx.md" --locate "表格召回是95%"
```

**批量补位置标注用 `tools/batch_locate_quotes.py`，不要手写。** 一页 source 常有几十到两百条摘录，逐条跑 `--locate` 不现实：

```bash
# 先干跑，看有多少条能定位、哪些搜不到
python3 tools/batch_locate_quotes.py --page "wiki/sources/xxx.md"

# 确认「无法定位 0」后再写回
python3 tools/batch_locate_quotes.py --page "wiki/sources/xxx.md" --write
```

它会读页面的 `source_path` 找原文，自动识别标位方式（录音清洗稿 → `第 N 段「段首十字…」`；智能纪要 → `@说话人 N MM:SS`），写完仍要跑第 5 步的硬自检。

外部文章类素材用 `--locate` 也有办法：原文只要有 `##` 级小节，它会额外给出这一段的 `§标题路径`（如 `〔§APPLYING THIS TO YOUR CONTEXT / CLAUDE.md〕`，落在首个 `##` 之前则给 `〔§开篇〕`）。清洗稿与智能纪要通篇只有 H1、没有小节，工具不会对它们给 `§` 建议——那类素材的正解是段号 / 时间戳。

⚠️ **它的匹配比校验器宽松**，可能出现「干跑报无法定位 0、校验器仍报搜不到」的情况（实测：标点差异如 `好，那这里` vs 原文 `好。那这里` 会被放过）。所以 `--write` 之后必须跑 `verify_source_page.py --page`，以校验器为准。

⚠️ **报「搜不到」时，先怀疑自己改了原文，而不是原文错了。** 实测 15 条搜不到的摘录里，13 条是把 ASR 噪声顺手"修顺"了（例如把「美满减」改成「每满减」），2 条是标点差异。正确的改法是把摘录改回原文的写法——**宁可留着错字，也不改字**，然后在页面「素材的可用边界」里列出还原对照。

**摘什么（按优先级）**：数值、因果判断、反例、条件限定、决策依据。

**不摘**：开场白、寒暄、指代不明的半截话、纯流程复述。

⚠️ **源材料作者的判断、经验、结论必须原样保留**——那就是源材料的内容本身，不是「掺判断」。只清掉**你自己（写页的模型）**的评价与推论。
（旧规范写「证据里不能掺判断」，被实现按最严读法执行，结果 40 页里 0 条摘录含数值。）

### 第 4 步 · 写页面

按本 Skill 定义的章节写。三处最容易写错：

- 摘录必须是**能在原文里逐字搜到的连续文本**。转述不算摘录。
- 每条摘录后写「**可用于支持：**」，指明它能支撑哪个断言。没有用途的摘录不摘。
- 「素材的可用边界」必须写**不能支持什么**，并与 `reliability` 呼应。

**摘录必须写成这个形状**（工具靠它代你机检）：

```markdown
- 「原文里逐字复制来的连续文本」〔第 14 段「做单元格的罩护。明确…」〕
  **可用于支持**：这条摘录能支撑哪个断言。
```

摘录行以中文引号开头；一条 bullet 下可放多条摘录，承接行也要以 `「` 开头（工具只认这种行，因为中文的 `「」` 也用作强调）。摘录写在一行内——原文的换行不影响比对（工具忽略空白差异），但**不要改字、补标点、修 ASR 错字**，改一个字就不再是原话了。摘录超过 15 条时可用 `###` 按主题分组。

字段与正文结构见本 Skill 的骨架和自检说明；可运行的虚构 source 示例见 `wiki/sources/示例素材.md`。

### 第 5 步 · 硬自检（不可跳过）

```bash
python3 skills/wiki-source-page/scripts/verify_source_page.py --page "wiki/sources/xxx.md"
```

脚本机检：frontmatter 必填字段与废弃字段 / sha256 是否与原文一致 / **每条摘录能否在原文逐字搜到** / 位置标注的段号与段首 10 字是否正确 / 是否残留「自行全文检索」占位符。

**有 FAIL 就必须修完再交付，不许带着 FAIL 收工。** 修好重跑，退出码 0 才算完。

脚本验不了「编译封闭性」——那一步只能人工回答第 2 步的三个问题。

## 硬规则速查

| 规则 | 判据 |
|---|---|
| 摘录必须逐字可搜 | 拿去原文搜，搜不到作废（脚本会代搜） |
| 不设长度上限 | 以保住一个完整判断为准，通常 50–300 字 |
| 位置必须写实 | 有章节号用章节号；智能纪要用时间戳；录音清洗稿用「第 N 段 + 段首 10 字」；外部文章用 `§标题路径`（开篇写 `§开篇`） |
| 源材料判断必须保留 | 只清作者自己的评价 |
| 冻结语义 | 一页素材一页 source，永不追加 |
| 按素材命名 | 不存在「RAG 的 source 页」，只有「某份素材的 source 页」 |

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 从原文开头顺着摘 | 摘到寒暄和半截话 | 先做第 2 步「从下游反问」 |
| 摘录写成转述 | 无法核验原话，等于没摘 | 从原文复制后跑脚本校验 |
| 「位置」写「请自行全文检索」 | 定位栏形同虚设 | §5.2 分档写实位置（脚本会判 FAIL） |
| 把源材料的判断也清掉 | 下游拿不到可用材料 | 只清自己的评价 |
| 往旧 source 页追加新内容 | 证据被污染，溯源失效 | 新内容进 concept 页，另建新 source 页 |
| 忘填 `sha256` | 无法增量，每次全量重跑 | ingest 前先算哈希 |

## 边界

| 你想写的 | 该去哪 |
|---|---|
| 原文说了什么（含原话、数值、案例） | **这里** |
| 原文里的概念展开讲 | `concepts/` |
| 原文提到的工具是什么 | `entities/` |
| 你对原文的看法 | `wiki/notes/` |
| 这篇 + 那篇合起来能得出什么 | `synthesis/` |

## 检索策略

| 场景 | 行为 |
|---|---|
| 一般提问（「RAG 是什么」） | **不命中 source**，命中 concept 页 |
| 要原话、要出处 | 下钻 source 层 |
| 关联计算 | source → concept 的出链**不计入关联边** |
