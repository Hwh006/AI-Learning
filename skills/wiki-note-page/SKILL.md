# Notes：把一个知识点讲清楚，并让读者找到相关知识点

## 什么时候应该调用

- 原文、转写或对话在回答：**遇到什么情况，应如何判断或完成某类功能、系统或项目**。从原文识别的操作性内容先起草为 `status: draft`，供用户回看；用户明确限定本次不保存时不写入。
- 用户要求保存、拆分、合并、重写或确认已有 note。
- 需要检查一条方法论的当前版本、历史版本和检索资格。

判断重点是**内容是否能指导下一次类似任务**，不是方法是否来自用户亲历。方法论可由原文、已有知识和可追溯证据推导，也可被新知识重建。原文只讲一个项目时，可提炼可迁移的条件与动作；无法提炼时保留为项目实例，不强写方法论。

## 什么时候不该调用

- 只解释事实、术语或机制，没有可执行动作：归 `concepts/`。
- 只概述一份素材说了什么：归 `sources/`。
- 只记录某一次项目的设计或执行，无法抽出适用条件：归 `solutions/`。
- 只有态度或口号（如“多关注质量”），没有可完成的动作；或只把文章目录改写成步骤。
- 仅因原文有多个标题、篇幅很长，或作者列了编号，就逐节建 note；原文分节是取证线索，不是页面边界。
- 把已有 note 当原始素材再次提取，或为了填满模板编造不存在的步骤、输入和阈值。

## 从作者目标到维度，再判断 note 边界

先重建原文主线：作者要完成什么目标，为什么采用这套方案，为达成目标分别讨论了哪些能力或工程维度，各维度又包含哪些知识点，它们是并列、前置、互相验证，还是同一方法的不同环节。原文标题可用于定位，不能直接决定页面数量。主线页可以概述作者的论证并提供深入阅读入口；若只是换句话复述全文，留在 source 页，不另写一篇 note。不要把并列维度伪装成必须依次执行的步骤。

**维度能否独立成篇**：把它从主线抽出，只需简短交代前提，读者仍能理解它解决的问题、包含的关键知识点，并据此形成可复用的判断或做法，就可写成深入 note。它不必有与原文不同的终极目标；同一总目标下的提示与工具设计、有效评估和生产可靠性也可能各自成篇。原文只提出关键方向、未给完整实践时，可在证据允许的范围内继续推到“以后遇到类似问题怎么做”，把必要的工程推导标为 `INFERRED`。若只有维度名称、无法形成有依据的具体方法，先保留在主线或列为候选，不用泛泛几句凑页。

**何时合在一篇**：若一个维度的判断和动作脱离另一个维度就无法讲清，拆开会重复核心论证，或几个点共同构成同一实践的原因、动作、分支和验收，就放在同一 note 内按子知识点展开。有前后因果不自动要求合并：能用少量前提说明依赖、正文仍可独立指导行动的两个维度，可以分篇并在需要的位置相互链接。拆分不由篇幅、段落数、标题数或单份素材数量决定；拆前查重，已有同义页可承接时合并。

**本次材料的校准例子**：Anthropic 为做好开放研究中的多智能体系统，分别讨论任务适配、研究架构、代理提示与工具、有效评估、生产可靠性；同步等待与异步协作是生产工程中的进一步取舍。这些维度可通向深入 note，但不是六个必须串行执行的阶段。用户提供的《工具故障后的调整、续接和运行中更新》围绕生产可靠性展开状态、门禁、Trace、恢复、异步交接和发布，六项共同回答长任务怎样可靠运行，应在一篇里讲清。另写的“是否异步化”只有在能独立说明瓶颈、收益、协调成本与验证办法时才成立，并与可靠性页交代交接和错误传播的关系。

**落到页面计划与阅读路径**：在 ingest 计划中，独立候选按 `create`、`merge`、`skip`、`review` 记录；页内子点进入承接页的证据需求与写作范围，不伪装成单独页面动作。主线列明各维度之间的关系并链接对应深入 note；深入 note 开头给出主线及真实相关页入口，正文只展开自己的方法，不复制主线或邻页。同一原文支持多篇时，每篇保留自己的证据范围和来源边界。

**串联其他 Wiki 页型**：note 的目录连接同组方法页，正文还要根据读者的问题连接相关的 `concept`、`solution`、`comparison`、`entity` 等页面。先用元数据找少量候选，再回读正文判断具体关系：读者要理解机制时连到 concept，要看作者或项目怎样落地时连到 solution，要作选择时连到 comparison，要核对产品范围时连到 entity；来源证据连到 source。链接放在产生该阅读需求的论述处，并说清目标页能回答什么。仅共享标签、来源或主题词不足以建链；已有合适链接不重复写，只有另一方向确有阅读入口需求时才补回链。`map` 仍只用于导航，不充当知识关系。

## 执行流程

1. **取证与查重。** 读原文、相关 source、`index.md`、`tools/wiki_lookup.py` 的候选结果和同主题 note；对可能串联的 concept、solution、comparison、entity 等页先看元数据，再回读少量相关正文。记录关键陈述及原文位置，区分原文直接说明、多个材料归纳和模型推导。拿不准是否为 note 候选时读 [`references/recognizing-note-material.md`](references/recognizing-note-material.md)。
2. **确定页面边界。** 先画出作者目标、维度、知识点和维度间的依赖，再做上面的抽离判断。写出主线页与每篇深入 note 各自回答的问题，以及哪些子点留在同页；再决定合并或拆分、拟标题。主线页说明关系并给出入口，不代替详细方法；深入页开头链接主线及相关维度。
3. **提取并组织子知识点。** 主线页交代每个维度为什么支撑作者目标、与其他维度是什么关系，以及从哪里继续深入；不在主线复制所有操作细节。深入页对本维度的子点保留触发情境、关键判断、原因或机制、涉及的角色和对象、具体动作、例子或失败场景、如何判断有效。原文没有某项时不编造。多个动作有依赖才按步骤排；可并行的点按分论点写；互斥条件写成分支。尤其不要把几个不同机制塞进一个“做什么”字段后各缩成一句。
4. **补必要连接，保留边界。** 原文没明确给出的连接动作，先检查没有它是否无法执行、有什么依据、是否存在同样合理的替代路径。确有必要才写，并标为 `INFERRED`；未定参数、来源冲突与替代分支如实保留。直接依据标为 `EXTRACTED` 并给可回读位置。不要从局部动作推成完整的规划到上线流程。
5. **写成能独立理解的正文。** 主线页让读者看清作者目标、维度出现的原因与彼此关系；深入页让读者看清“为什么要这样做 → 具体怎么做 → 遇到例外怎么办 → 怎么判断起作用”的因果链。用具体场景、输入与产物把抽象词讲实；必要时用表格对照状态或角色。可以用段落、列表、表格或小标题，不要求每点套同一组字段。已有上下文说明过的内容不重复填格，也不把复杂判断压成“执行检查”“做好恢复”这样的短句。
6. **回读与验证。** 暂时放下原文，只读新 note：能否说清它解决什么问题，为什么该做，在哪些条件下该怎么做，什么证据支持，怎样发现无效或误用？若一句话需要读者自行猜含义，就补上原因、对象、例子或可检查的结果。再对原文核对是否遗漏改变做法的细节，检查跨页关系是否成立、链接是否真实且位于读者需要的地方；沿 note → concept / solution 等路径实际找一次所需内容。新页为 `draft`；用户确认后才改 `verified`。完整示例见 [`references/example-methodology.md`](references/example-methodology.md)，它是虚构教学材料。
7. **修订与版本。** 新知识或对话改变前提、步骤、顺序、完成判据或适用范围，导致照旧版执行可能出错时升版；文字润色、补链接等不改变行动的方法就地修订。升版时把旧版复制到 `wiki/notes/_history/{名称}-v{旧版本}.md`，在旧版 frontmatter 标 `searchable: false`、`superseded_by: wiki/notes/{当前文件}.md`、`valid_until: YYYY-MM-DD`；当前路径保持稳定，版本号递增，`searchable: true`，更新 `updated`、版本历史及当前版元数据。旧版不再修改或作为事实来源。新版本若含未经用户确认的推导，仍为 `draft`；`searchable: true` 仅表示当前版可被检索，不等于内容已核准。当前版可供其他页面引用，但引用时保留其状态和依据边界，不能把它当原始素材重新 ingest。
8. **校验与交付。** 从项目根目录运行 `python3 skills/wiki-note-page/scripts/verify_note_page.py --page 'wiki/notes/{文件}.md'`；升版后运行 `--all` 与 `--chain '{标题}'`。脚本检查元数据、版本和链接，不能判定拆分是否合理、因果是否讲清、证据是否真的支持结论；这些由 Agent 回读。交付时给用户可打开的每篇地址、合并或拆分理由及待核项。

## 页面骨架与写法

固定的是**元数据、一个明确的主问题、可追溯依据与版本**，不是每段都用相同的六栏。页型职责与边界以 [`index.md`](../../index.md#页面放在哪里) 为准。主线型正文可按“作者目标 → 能力维度 → 维度关系与深入入口”组织；深入方法正文可按子知识点及实际依赖组织。以下骨架只是可选的小节示意，判断型 note 仍按判断、理由、依据和失效条件组织。

```markdown
---
type: note
note_type: methodology
title: {中文主知识点标题}
tags: [{能从正文找到依据的具体主题词}]
sources: [{真实原文或 source 路径；无外部来源时填 []}]
author: human
status: draft
version: 1
searchable: true
created: {YYYY-MM-DD}
---

# {中文主知识点标题}

> 在什么场景，解决什么问题，得到什么结果。

## 本组知识点目录
只在确有相关独立 note 时，简短写出各页解决的问题并链接真实页面；当前页用文字标示，不自链。

## 适用场景与问题
读者为什么在此时需要这篇；不适用条件或必要输入只写会改变判断的部分。

## {由内容决定的论点、分论点或实际步骤}
解释问题、判断、原因与做法；可用具体场景和检查方法说明，保留例外与来源边界。

## {另一子知识点或分支}
……

## 失效边界
哪些条件改变会使方法失效，哪些关键事项仍待核。

## 版本历史
| 版本 | 日期 | 改了什么 | 为什么 |
|---|---|---|---|
| v1 | {日期} | 首版及来源范围 | 首次起草 |
```

以上是内容安排示意，不是供逐字填充的模板。无同组 note 时不写空目录；已有开篇目录时，页尾不必再复制一份“相关”。真正是顺序流程时可用 `## 步骤` 和 `### 步骤 N`；若是并列的知识点、判断条件或故障分支，应按它们实际关系命名标题。每个关键行动仍要使读者找得到所需输入、动作、产物、继续或停止条件，但可以在连续正文中说明，不必拆成六条标签。没有材料支持或不适用的信息，不留空字段，也不为填表编造内容。

**展开示例**：只写“在交接处设置门禁，检查产物后进入下游”会丢掉判断对象和原因。应说明下游实际依赖哪份结果、为什么子 Agent 说“完成”不等于结果可用、代码核对文件及版本而 Agent 核对证据、缺失或过期时怎样处理，以及修复后用什么记录证明现在可以继续。长度由这些必要信息决定，不设每节字数下限。

## 自检清单

- [ ] 已还原作者目标、支撑目标的维度、维度内知识点及关系；没有把原文章节直接当页面边界或把并列维度排成假步骤。
- [ ] 深入 note 抽离主线后仍可说明问题和实践；不能独立讲清的原因、步骤、分支与验收留在承接页内。
- [ ] 开篇目录只链接真实且相关的独立 note；当前页不自链，目录不代替正文；读者可从旧入口找到新页。
- [ ] 已回读相关 concept、solution 等候选正文；在需要解释机制、查看实例或作选型的论述处落链，读者可沿链接找到所需内容，无重复或仅凭标签建立的关系。
- [ ] 主线页解释每个维度为何出现及其关系；深入页把子知识点的“是什么、为何、怎么做、如何判断”讲清，而不是几个套模板的短句。
- [ ] 方法的行动依赖由真实输入输出决定；可并行与条件分支不伪装成线性步骤。
- [ ] 保留会改变执行的角色、对象、条件、交付物、例外和停止信号；原文没有的细节不补成既定要求。
- [ ] 原文直接说明、跨材料归纳和工程推导可区分且能回溯；不确定处说明缺什么以及影响哪项判断。
- [ ] 新页保持 `draft`；修订时核对是否需要升版，旧版不再可检索。
- [ ] 脚本检查通过，并由 Agent 回读内容质量、页面边界与入口链接；交付时给出实际文件地址。
