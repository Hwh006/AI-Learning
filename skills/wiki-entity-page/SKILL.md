# entity 实体页（符号表）

## 一句话定位

entity 页 = **wiki 的符号表条目**。符号表里所有出现过的标识符都登记进去，**有且只有一条**，记它的定义、用途、生命周期；任何地方引用这个名字，都解析到同一条目。

写得好不好，只看一条（02 §0 的完备性标准）：

> **给定一个对象名（或其任一别名），全库只有一页承接它；读完这一页，知道它是什么、什么场景用它、它现在还有效吗。**

**它不写论述。** 符号表条目不写论文——薄页（只出现在一张选型表里）和厚页（素材给了完整定义）都合格。往深了写是官方文档的活。

**职责分工**：`index.md` 统一定义页型职责、适用条件和边界；本 Skill 定义本页型的字段、章节、执行步骤与校验。分类冲突按 `index.md` 处理，写作结构以本 Skill 为准，并同步修正不一致内容。

**标签自检**：写入或修改 Wiki 页时，按项目 `AGENTS.md` 的标签规则，从本页主旨、反复讨论的对象与关键机制提取具体检索词；每个主题标签须能在正文找到依据。素材类型标签另保留，不能单独充当主题标签。

| 本 skill 自带 | 什么时候看 |
|---|---|
| `scripts/verify_entity_page.py` | 每一步都用：反扫、查重、名称解析、成页自检 |

## 触发条件

用：

- 一份素材 ingest 时，要找出它提到了哪些具名对象
- 给某个工具 / 产品 / 机构 / 人物 / 论文 / 事件建页或合并页
- 用户问「XX 是什么」「课程里怎么说的」「这个东西在库里有没有页」
- 排查同一对象被建多页、或长尾对象一直没建页

不用：

- 只是讨论、回答概念问题 → 不写页
- 要写原理（RAG 是什么）→ `concepts/`
- 要写素材原文说了什么 → `sources/`
- 要写两个工具怎么选 → `comparisons/`

## 输入契约

必填：

- **工作目录**：项目根。脚本路径（`skills/wiki-entity-page/…`）、素材路径（`raw/…`）、输出路径（`wiki/entities/…`）都相对它。
- **启动场景**：单份素材 ingest（→ 用 `--scan`，只扫这份）还是全库补建（→ 用 `--scan-all`）。两者产出差别很大。

补齐项：

- **素材范围**：使用者自行提供的 `raw/` 原文；口语转写中的数值与术语须结合上下文核对。
- **已有符号表**：`wiki/entities/` 当前是空的（3 类 0 产出之一）。所以**第一次跑必然全是「待建页」**——这不代表 123 个都要建，见第 2 步。

## 执行流程

### 第 1 步 · 反扫对象（不要等"想起来"再建页）

旧规范没有任何一步去问「这份素材里出现了哪些具体对象」——这是 0 产出的直接原因。固定跑：

```bash
# 单份素材（ingest 时用）
python3 skills/wiki-entity-page/scripts/verify_entity_page.py \
  --raw "raw/record_cleaned_markdown/企业知识库与RAG讨论.md" --scan

# 全库（补建时用），默认只列出现在 ≥2 份素材里的
python3 skills/wiki-entity-page/scripts/verify_entity_page.py --scan-all
```

输出是一张按「未登记优先、跨源份数降序」排序的候选表，带类型与置信度。

**"候选"不等于"该建页"。** 这份清单的作用是**防止漏掉长尾对象**，不是待办列表。它会在结尾提醒你排除泛称与概念。

一条实测结论，值得记住：**中文产品名多数不带后缀**（豆包、元宝、飞书、通义都不带），正则抓不到，脚本靠一份有限的兜底词表补——**词表命中不了的中文长尾仍需人工扫**（见「已知限制」）。

### 第 2 步 · 核对名称（这一步不能省）

素材是录音转写，**ASR 会把工具名转错**。真实案例，`企业知识库与RAG讨论` 原文：

> 「就这几家，face、MySQL、Elasticsearch」

`face` 实为 **FAISS**、`MySQL` 实为 **Milvus**——一句话里两个工具名都错。照字面建页会建出 `face.md`。

```bash
python3 skills/wiki-entity-page/scripts/verify_entity_page.py --context "MySQL"
```

这条命令会把该词在全部素材里的上下文打出来。上面那个例子里 4 处 MySQL 有 3 处指真数据库、1 处是 Milvus 的错字——**工具负责把歧义摆出来，判断必须由人做**。

同时按 02 §8.1 排除掉不该建页的：泛称（「向量数据库」「这个系统」）、原理（RAG、MCP）、机构举例（「抖音怎么做的」这类只是引用，不是要给它建页）。

### 第 3 步 · 查重与解析（符号表的第一职责）

```bash
# 看符号表全貌 + 查重名冲突
python3 skills/wiki-entity-page/scripts/verify_entity_page.py --registry

# 名称解析测试：这个词落到哪一页？
python3 skills/wiki-entity-page/scripts/verify_entity_page.py --registry --check "Dify 平台"
```

- 命中 → **合并进已有页**，把新的叫法补进 `aliases`
- 未命中 → 新建（**单源也建**）
- 报 `冲突!` → 同一对象已有多页，先合并再往下走

⚠️ **本机文件系统大小写不敏感（已实测）。** 写入 `faiss.md` 会**直接覆盖**已存在的 `FAISS.md`，不报错。所以「大小写不同的两个文件并存」在本机发生不了——真实风险是**静默覆盖，丢掉已有页面内容**。`--check` 会专门检这一条。

### 第 4 步 · 按七节骨架写页

固定顺序，不要自己发明结构（02 §3）。逐节的写法、格式、颗粒度与 ✅❌ 对照都在规范 §4：

```
# {对象通用名}
> 一句话定位          ← 类型 + 用途，一行，≤40 字
## 是什么              ← 1–3 句；素材没有就标「素材未提供定义」或补 〔素材外〕 硬事实
## 关键事实            ← 表格：属性 | 值 | 来源
## 素材中的定位         ← 场景：理由 〔位置〕    ★本页核心
## 出现记录            ← 表格：素材 | 说法 | 位置
## 生命周期            ← 必答：当前状态 / 依据 / 最近变动
## 相关                ← 3–8 个 wikilink
```

三处最容易写错：

- **「素材中的定位」是核心，不是「出现记录」。** 素材里最富的就是选型表/推荐表，它的组织方式就是「什么场景用什么」。旧规范写成「不同素材中的观点」对照表——那把互补场景误读成争议了。
- **不写对照。** 「FAISS vs Milvus 怎么选」属于 `comparisons/`，本页只写一句 + 出链。
- **生命周期不许省略、不许写「暂无」。** 写成「未知」+ 一句依据。具体对象会改名/停用/迭代，原理不会——**这是 entity 区别于 concept 的唯一硬边界**。

位置标注格式**沿用 01 的分档**（结构化材料用 `§二.2.4`、口语转写用 `第 N 段「段首十字…」`、智能纪要用时间戳、外部文章的**无编号章节**用 `§标题路径` 如 `〔§Now: Design interfaces〕`，全文无小标题时用 `§开篇`），本页不另立一套。位置不要手工数，用 01 的 `--locate` 取。

⚠️ **entity 页天然多源，所以位置标注必须带来源短名**：写 `〔文档解析探讨 第 30 段「最好的开源知识库，没…」〕`，不要只写 `〔第 30 段「…」〕`。段号是**那一份原文**的段号，不带短名读者（和校验脚本）无从判断该去哪份原文里数第 30 段。`出现记录` 表格的「位置」列若并排写多段，段号同样按**该行「素材」列那一份**计。

> 这条不是洁癖：校验脚本早期把该页所有来源的段落拼成一张表再按段号取，导致多源页从第二个来源起全部误报「段首与原文不符」（实测 8 页 10 条假阳性）。现已改为按短名分源解析，但**不写短名就没有分源依据**，仍会退回合并表兜底。

字段与正文结构见本 Skill 的骨架和自检说明；可运行的虚构 source 示例见 `wiki/sources/示例素材.md`。

### 第 5 步 · 硬自检（不可跳过）

```bash
python3 skills/wiki-entity-page/scripts/verify_entity_page.py --page "wiki/entities/FAISS.md"
```

脚本机检：frontmatter 必填与废弃字段 / `lifecycle` 枚举 / `corroboration` 与「出现记录」行数是否自相矛盾 / **七节骨架** / 生命周期是否被占位语糊过 / 关键事实的「来源」列 / 位置标注能否回溯到原文 / 评价词与推测词 / `〔素材外〕` 是否有隔离声明 / `aliases` 该不该记 / **有没有入边**。

**有 FAIL 就必须修完再交付。** 修好重跑，退出码 0 才算完。

### 第 6 步 · 回填出链（不做就是孤岛）

entity 是**被引用方**，不是入口。没有入边它就是一页检索不到的孤岛：

| 引用方 | 何时出链 |
|---|---|
| `concepts/` | 正文首次提到具体工具/产品处 |
| `solutions/` | 技术选型/架构章节里每个具名组件 |
| `comparisons/` | 对比对象的每一行 |
| `sources/` | 「关键概念」节不只挂概念，**对象也挂**（标 `[待创建: [[名称]]]`） |
| `entities/` 的元数据 | `title` 与 `aliases` 能被检索，且相关内容页有真实出链 |

> 这一层目前**没有入边也没有出边**：全库 9 份规范里除 02 自己外没有一份提到 entity，目录登记不能代替内容页的真实入边。判据写对也不会有人走到它——所以第 6 步是必做项，不是收尾。

## 硬规则速查

| 规则 | 判据 |
|---|---|
| 唯一性优先于完整性 | 宁可条目少，不可重复。去重是第一职责 |
| 出现即登记 | 不"等第二个来源"。多源是属性（`corroboration`），不是准入门槛 |
| 生命周期必答 | 未知也要写 `unknown`。这是 entity 与 concept 的硬边界 |
| 只写这一个对象 | 选型对照 → `comparisons/` |
| 素材的判断要保留 | 讲师说「不适合 XX 场景」是素材内容，要摘；「它很好用」是你的评价，不写 |
| 位置必须写实 | 不用 〔〕 也要能给出来源；脚本会核对 |
| 建完回填入边 | 不然是孤岛 |

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 不查重就新建 | 同一对象多页，引用不一致 | 先 `--registry --check` |
| 按小写文件名新建 | **静默覆盖**已有页（本机大小写不敏感） | 大小写与已有页保持一致 |
| 不记别名 | `Dify` / `Dify 平台` 各一页 | 素材里的别的叫法全进 `aliases` |
| 因单源而不建页 | 长尾对象永久缺失（现状：0 产出） | 单源也建，标 `corroboration: 单源` |
| 照字面建页 | 建出 `face.md`（ASR 错字） | 第 2 步 `--context` 核对 |
| 生命周期写「暂无」 | entity 退化成弱 concept | 写「未知」+ 依据 |
| 把互补场景写成「两种说法」 | 像在报道争议，读者仍不知道何时用 | 按场景汇总 |
| 把选型对照写进来 | 与 comparison 重复，两处维护 | 只写单对象定位 + 出链 |
| 写「它很好用 / 不如 XX」 | 无源评价 | 评价进 `wiki/notes/` |
| 性能数字不带口径 | 课堂口述被当成权威参数 | 抄数字 + 标「无测试条件」 |
| 建完页没有入边 | 孤岛，检索不到 | 第 6 步回填 |

## 边界

| 你想写的 | 该去哪 |
|---|---|
| 这个对象是什么、什么场景用 | **这里** |
| 它背后的原理展开讲 | `concepts/` |
| 它和别的工具怎么选 | `comparisons/` |
| 它在某个项目里怎么用的 | `solutions/` |
| 素材原文说了什么 | `sources/` |
| 你对它的评价 | `wiki/notes/` |

## 检索策略

| 场景 | 行为 |
|---|---|
| 「XX 是什么」 | 命中 `entities/` |
| 「XX 怎么选」 | 命中 `comparisons/` |
| 「这个工具课程里怎么说的」 | entity → source 下钻 |
| 去重解析 | 查询词先过 `aliases` 展开，再匹配页面 |
| 关联计算 | entity↔concept **不计关联边**（表示「某原理涉及某工具」，不表示两个概念相关） |

## 已知限制（必须告诉使用者）

1. **中文无后缀专名靠词表兜底，词表有限。** 正则只能可靠发现「拉丁词 + 中文机构后缀」两类。豆包、元宝、飞书这类不带后缀的中文产品名靠 `SEED_CN`（本项目语料实测命中的约 40 个）。**词表之外的中文对象扫不出来，必须人工扫标题与表格。**
2. **中文产品后缀通道已弃用。** 「XX平台/XX系统/XX助手」在这份语料里几乎全是误报（抓出来的是「通过大模型」「客服系统」这种动词短语和泛称），已从脚本移除。这是取舍，不是遗漏。
3. **低置信标记不等于否定。** `BGE`、`LoRA` 这种缩写会被标成低置信，只是提示要核一眼，不代表不该建页。
4. **脚本验不了最后一问。** 「读完这一页，知道它是什么、什么场景用、现在还有效吗」——这句只能人工回答。
