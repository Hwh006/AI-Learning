# 知识文章写作

让读者看懂一个具体问题怎样发生，理解关键机制，并能在自己的场景中作判断。读者得到的应是一条能走通的解释，不是一串术语和口号。

本 Skill 按[女娲的主题蒸馏方法](https://github.com/alchaincyf/nuwa-skill)从用户指定的 24 篇文章提炼；21 篇用于归纳，3 篇留出验证。样本都来自“银翼AI评测室”，集中于 AI 评测。方法可尝试迁移到产品、业务和其他知识主题，不能据此声称覆盖所有知识写作，也不模仿该账号身份。样本内的新闻、数字、技术结论与作者亲历没有在本次蒸馏中独立证实。

需要选择论证方式、核对规则出处或处理例外时，读[写作规则与证据](references/writing-methods.md)。需要研究某篇如何展开时，由[来源清单](references/source-index.md)定位外部原文链接；公开版不附文章全文与图片。只加载当前任务需要的参考，不默认读取全部语料。原文只用于理解方法，不拼接原句生成新文。

## 接到任务先确定什么

识别用户要新写、改写还是只讨论，再确定读者要解决的一个问题、已有材料及用户指定的发表形式。未指定读者时默认产品与 AI 从业者；不默认文章一定写 AI 评测。篇幅随用户目标和材料密度，不为凑字数增加同义解释。

新写时，从主题中找读者正在作的判断，例如“补货点怎样定”“状态相同为什么还要留事件”。改写时，先保留原稿的有效主张和具体材料，再修复因果、缺证与结构；不要把有价值的业务细节洗成通用散文。只请求一段、一个标题或短答时，完成对应片段。

题目足够清楚就直接推进。只有会改变事实或文章方向的缺口才追问；能从材料取得的答案先查材料，不要求用户填一张完整需求表。

## 1. 先弄清材料能支持什么

动笔前在内部区分四类内容，不要求用户看这张分类表：

| 内容 | 处理 |
| --- | --- |
| 用户确认的事实、可回读记录和已核验公开资料 | 可以承担事实段落；重要数字、引语和外部判断保留出处与时间条件 |
| 原文作者声称的案例、数据或因果 | 仍是待核实的来源主张；需要作为新稿事实时回查原始证据，不能用写作样本本身担保真实性 |
| 作者的分析与推演 | 写清依据、成立条件及可能的其他解释，不能冒充实际发生的结果 |
| 为解释而构造的例子或教学数字 | 可以使用，但应在例子开始处说明“假设”“例如设定”，数字和条件前后一致，不加虚构客户对白或现场 |

用户未提供的第一人称亲历、实施结果、客户原话和效果百分比不能补造。草稿中已出现这些说法，也要检查依据。具体人物、产品现状、新闻、价格、研究数据等需要事实核验时，使用可用检索能力查可靠原始来源；不把样本中的数值当可直接搬用的参数。

材料不足时，优先补可取得的依据，再缩小题目或交付有边界的短稿。若用户禁止追问且没有检索能力，简短说明无法支持原题中的事实承诺，提供明确标为假设的解释稿或可成立的较窄题目；不能把架空案例写成真实项目以满足篇幅。

## 2. 找到一条能被解释的主张

在内部用一句普通话说出“读者困惑什么、哪个机制能解释、看懂后能改变什么判断”。主张来自材料，不先造一个宏大结论再搜例子凑证据。

用一个可见现象、具体任务或确有依据的反差开篇，尽快指出知识缺口。没有真实误解或冲突时，直接解释问题，不编造“所有人都以为……”或制造危机。标题承诺的内容必须在正文中兑现，不能用“终极”“标准答案”替结论担保。

## 3. 按问题选择组织方式

结构取决于读者要知道什么，不要求每篇固定几层、几步或几节：

| 读者的问题 | 合适的展开路径 |
| --- | --- |
| 为什么会出这个问题 | 可观察症状 → 发生过程 → 关键成因及竞争解释 → 如何定位或验证 |
| 一个概念或系统是什么 | 它解决的任务 → 必要组成及关系 → 沿一个例子走一遍 → 哪些情况不适用 |
| 一套方法怎样使用 | 输入和前提 → 关键动作及其原因 → 输出与检查方式 → 失败时怎么调整 |
| 几种做法怎样选 | 共同问题 → 相同维度比较 → 各自代价与条件 → 给定场景下的选择依据 |
| 一件事能说明什么 | 核实的事件 → 机制解释 → 证据不能说明的部分 → 对读者决策的有限启发 |

只引入与主张有关的模块。分层时解释每层为何存在、与相邻层如何衔接；分类时用一致的比较维度，避免把角色、阶段和效果混成同一级清单。

## 4. 把知识写成能跟随的解释

以下动作按当前难点选择，不把它们强制拼成每段模板：

- 从具体症状走到机制。讲清谁在什么条件下做了什么，信息或状态在哪一步改变，怎样产生可见后果。原因未查明时保留多种解释，不靠语气确定根因。
- 尽量让一个例子贯穿相邻环节。先给足条件，再追踪它如何变化；需要比较时只改关键条件，让读者看出差异从哪里来。换例子时说明是在测试哪个边界。
- 术语先承担解释任务，再给名称。首次出现陌生概念时，用一句话说清它管什么、能看到什么；英文缩写不是解释。
- 类比帮助建立关系后，返回准确概念，指出重要的不对应处。不要用人的器官、考试或流水线的比喻推导系统必然怎样运行。
- 方法要落到可观察动作。说清输入、操作、输出或判断依据中真正影响理解的部分；“建立闭环”“加强治理”后面如果没有行为变化，就继续展开或删去。
- 每一段增加新信息：机制、例子、条件、证据或反例。段落长度和句式可以变化；避免整篇用相同的短句、反问或对仗表演洞察。
- 图、表、代码只在它们更容易表达流程、关系、比较或操作时使用。正文仍要解释图中关键关系；不照搬样本配色和大图数量，不把图片里的公式当成已经核验的事实。

语言默认专业而能直接读懂。保留领域中必要的术语、冒号、列表和代码格式，不继承其他写作 Skill 的机械标点禁令。语气的确定程度与证据一致，不靠夸张标题、假亲历或大厂名字增加可信度。

## 5. 把结尾写成知识的使用入口

回到开头的问题，选择最有用的一种收束：一个判断条件、一次排查动作、一个小范围尝试，或一个仍需验证的问题。建议说明适用前提，不把特定公司的实现直接推荐为所有团队的配置。

概念已解释清楚且没有行动要求时，可以停在准确的认识或边界上。不要强塞“马上做三件事”、营销引流、品牌署名或宏大升华。

## 6. 交稿前沿读者的理解走一遍

- 标题、开头、各节和结尾是否都服务同一个问题；读者为何需要下一段，能否顺着解释回答出来？
- 重要主张有材料支撑吗？事实、假设、目标、实测和推断是否可区分？精确数字的单位、条件和算术是否一致？
- 例子有没有真正演示机制，还是只把结论换成一个故事？有无遗漏会改变结论的条件、例外或其他成因？
- 是否堆了没有解释作用的分类、缩写或框架？删去重复主张后，文章还能顺畅推进吗？
- 是否照搬样本标志性句段、虚构第一人称、把所有题目写成 AI 评测，或把图片与代码提取缺陷当成写作习惯？

交付用户要求的标题与正文；只在影响使用时附少量待核事实或关键来源。除非用户要求，不展示内部提纲、规则编号、证据分类或自评分数。用户指定文件时编辑指定文件，否则在聊天里交稿；不自动写 Wiki 或个人记忆。

## 方法边界与复核入口

同账号多篇重复只能说明写法稳定，不能证明其观点正确或该写法对所有主题有效。样本中的第一人称经验、推广结尾、绝对化判断与未经证实的数据不进入默认写作规则。当前只验证了少量任务，不承诺固定传播或转化效果。
