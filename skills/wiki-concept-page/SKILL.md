# concept 概念页（标准库）

## 一句话定位

concept 页 = **wiki 的标准库**。可跨项目复用的原理与方法，接口稳定，被方案页 import。

它**不写**：某个项目的编排决策（→ `solutions/`）、某个工具的参数与版本（→ `entities/`）、两个方案怎么选（→ `comparisons/`）。

写得好不好，只看一条（03 §0 的完备性标准）：

> **给定一个业务问题（不是概念名）——「表格总抽不准怎么办」「上线基准定多少」——只用 concept 层（含其出链的 entity / solution），能不能拿到步骤、条件、数字口径、失败信号，而不需要回读 raw？**

**结构齐全不等于知识可用。** 现有 22 页的节骨架合规率是 100%，但 82 条出链全部指向 `concepts/` 内部、指 `entities/` 的 0 条；数字留存 0 条。

**职责分工**：`index.md` 统一定义页型职责、适用条件和边界；本 Skill 定义本页型的字段、章节、执行步骤与校验。分类冲突按 `index.md` 处理，写作结构以本 Skill 为准，并同步修正不一致内容。

**标签自检**：写入或修改 Wiki 页时，按项目 `AGENTS.md` 的标签规则，从本页主旨、反复讨论的对象与关键机制提取具体检索词；每个主题标签须能在正文找到依据。素材类型标签另保留，不能单独充当主题标签。

| 本 skill 自带 | 什么时候看 |
|---|---|
| `scripts/verify_concept_page.py` | 每写完一页必跑，见第 5 步 |

## 触发条件

用：

- ingest 某份素材时，它讲了抽象原理、机制、流程、方法论、指标
- 给某个机制 / 方法 / 指标建页，或把同义概念合并进已有页
- 用户问「XX 是怎么运作的」「XX 该怎么做」「这个数字什么意思」
- 排查同一机制在多页被重复展开、或 concept 提到工具却没出链

不用：

- 只是讨论、回答概念问题 → 不写页
- 要写素材原文说了什么 → `sources/`
- 要给具体工具 / 产品建页 → `entities/`
- 要写某类项目的端到端方案 → `solutions/`
- 要写两个方案的取舍 → `comparisons/`

## 输入契约

必填：

- **工作目录**：项目根。脚本路径（`skills/wiki-concept-page/…`）、素材路径（`raw/…`）、页面路径（`wiki/concepts/…`）都相对它，命令请在这个目录下执行。
- **概念名**，或指向概念的素材段落。用户只说主题时先用 `tools/wiki_lookup.py search` 按元数据查候选，再读已有页面，**不要凭主题猜名字**。

补齐项：

- **已有页面**：`wiki/concepts/` 现有 22 页。**建页前必查**，别名与近义名都要查（`--links` 会给全库名称清单）。
- **素材范围**：使用者自行提供的 `raw/` 原文；口语转写中的数值与术语须结合上下文核对。

## 执行流程

### 第 1 步 · 定范围与粒度（先决定「该不该建页」，再决定「该不该独立成页」）

```bash
# 查全库已有的概念名与别名，避免建重页
python3 skills/wiki-concept-page/scripts/verify_concept_page.py --links

# 看哪些页面被引用却还没建（sources 的「关键概念」节 + 全库 [待创建:]）
python3 skills/wiki-concept-page/scripts/verify_concept_page.py --stubs
```

两个判断，顺序不能反：

**① 该不该建页？** 判据只有一条：**它能否被复用**（03 §0 要求 1）。

| 建 | 不建 |
|---|---|
| 有可展开的机制 / 步骤 / 条件 | 只是泛称，没有内容可展开 |
| 换个项目依然成立 | 是某个项目的一次性编排决策 → `solutions/` |
| — | 是某工具的版本特性 → `entities/` |

> ⚠️ **不要用「出现频次 ≥2 次」当准入门槛。** 出现频次是属性不是判据：一份素材里讲透一个原理就够建页；出现在十份素材里但每次只有一句带过，反而说明它没有可展开的内容。（旧规范用频次做判据，是 22 页里大量「结构齐全但答不出问题」的来源之一。）

**② 该不该独立成页？** 走 03 §4.13 的三个测试，**任一通过即独立**：

| 测试 | 例 |
|---|---|
| **独立可答**：有人会单独问它吗？ | 「混合检索是什么」✅ / 「RAG 的第三步是什么」❌ |
| **独立边界**：它有自己的失效条件吗？ | 重排序有自己的失败模式 ✅ |
| **独立引用**：会被别的页面 `[[链接]]` 吗？ | 会被 ✅ |

不通过的 → **作为父页的一节**。判不准时按 §8.1 的「concept 还是 solution」再判一次。

### 第 2 步 · 从业务问题反推（不要从「素材讲了什么」往下切）

写之前先回答，**答案要具体**：

1. **有人会拿什么业务问题来查这一层？** 列 3–5 个。必须是提问形式：「表格抽不准怎么办」——不是「文档解析」。
2. **答那些问题需要什么材料？** 步骤？条件？**数字口径**？失败信号？
3. **素材里这些材料在哪？** 按 03 §4.15 定位。
4. **和已有页面重复吗？** 走 03 §4.13 粒度判据与 §4.14 合并规则。

跳过这一步的结果，是写出「结构齐全、闭卷答不出」的页面——现有 22 页的普遍状态。

### 第 3 步 · 抽取、定位与核对

**定位不要手工数段号**，用 01 的脚本取（位置格式两页共用一套，本 skill 不另实现）：

```bash
python3 skills/wiki-source-page/scripts/verify_source_page.py \
  --raw "raw/record_cleaned_markdown/企业知识库相关讨论.md" --locate "表格召回是95%"
```

**抽取优先级**：机制步骤 → 条件与前提 → **数值与口径** → 案例与反例 → 失败信号。

**口语素材必须核对**：ASR 会把术语转错。真实案例——`企业知识库与RAG讨论` 原文里 `face` 实为 **FAISS**、`MySQL` 实为 **Milvus**；`企业知识库相关讨论` 里「罩护」实为**召回**。要核对时：

```bash
python3 skills/wiki-entity-page/scripts/verify_entity_page.py --context "MySQL"
```

⚠️ **素材里讲师给的判断、结论、经验必须原样保留**——那是素材的内容本身，不是「掺主观」。只清掉**你自己（写页的模型）**的评价。旧规范按最严读法执行，结果是 22 页里 **0 条**含数字的失效边界。

### 第 4 步 · 按十节骨架写页

固定顺序，不要自己发明结构（03 §3）。逐节的写法、格式、颗粒度与 ✅❌ 对照都在规范 §4：

```
# {中文名称（必要英文术语）}
> 一句话定位              ← 做什么 + 解决什么问题，一行
## 是什么                  ← 2–4 句：类型 + 组成 + 与最近概念的差别
## 有什么用                ← 解决什么具体问题、可观察的结果
## 怎么运作                ← 输入 → 步骤 → 输出；有分支写条件     ★本页核心
## 怎么用                  ← 选择 / 配置 / 执行 / 检查
## 适用场景                ← 什么时候用，什么时候该选别的
## 容易混的点              ← 和什么混、差别在哪、造成什么误判      ★不能空
## 失效边界                ← 失效条件 + 代价 + 失败信号 + 数字口径  ★必写
## 来源与证据              ← 表：来源与位置 | 该来源提供的说法 | 置信度
## 相关                    ← 4–8 个 wikilink，含 entity 出链
```

四处最容易写错：

- **「怎么运作」要给输入输出，不是名词列举。** 「解析包含版面分析、表格识别、OCR 和整合」不合格；每步写清「输入什么 → 做什么 → 输出什么」。
- **父子页不重复展开。** 这一步会涉及混合检索、重排序——**写一句 + 出链**，展开属于它们各自的页。RAG 页现在把整条链路写了一遍，子页再各写一遍。
- **「容易混的点」不能空。** 概念越常用越容易和邻居混（OCR ≠ 文档解析 ≠ 多模态理解）。
- **「失效边界」必须带数字与口径。** 只写「数字不可信」等于没写——读者既不知量级也不知该不该信。写成「端到端约 **70% 多**——讲师课堂口述，无分母、无测量方法〔位置〕」。

**位置标注形状**（沿用 01 分档，多源页**必须带来源短名**）：

```markdown
〔第一节 §二.2〕                                    ← 结构化材料
〔企业知识库相关讨论 第 14 段「做单元格的罩护。明确…」〕   ← 口语转写
〔§二.2〕                                            ← 单源页可省短名
```

❌ **不要用 HTML 注释标来源**（`<!-- confidence: EXTRACTED | ... -->`）：阅读视图里不可见，等于没标。现有 18 页这么写。

**`concept_type` 决定额外要写什么**（03 §2）：

| 值 | 额外必写 |
|---|---|
| `机制` / `架构` | 步骤的输入输出 / 组件与数据流 |
| `方法` | 目的与输入、执行步骤、判断依据、案例、反例（§4.12） |
| `指标` | 衡量什么、怎么算、方向、阈值条件、**不能证明什么**（§4.11） |
| `术语` | 与近义词的边界 |

字段与正文结构见本 Skill 的骨架和自检说明；可运行的虚构 source 示例见 `examples/wiki-demo-source.md`。

### 第 5 步 · 硬自检（不可跳过）

```bash
python3 skills/wiki-concept-page/scripts/verify_concept_page.py --page "wiki/concepts/文档解析.md"
```

脚本机检：frontmatter 必填与废弃字段 / `concept_type` 枚举 / **九节骨架与顺序** / 「容易混的点」「失效边界」是否被占位语糊过 / **失效边界有没有数字** / 来源标注 `〔〕` 是否存在、多源页是否带来源短名 / **是否残留 HTML 注释来源** / 「来源与证据」行数与 `sources` 是否自相矛盾 / `相关` 节链接数与 `[待创建:]` 格式 / 评价词与推测词。

**有 FAIL 就必须修完再交付，不许带着 FAIL 收工。** 修好重跑，退出码 0 才算完。

脚本验不了 §0 那条——「闭卷能不能答出那 5 个业务问题」，只能人工回答（第 2 步 + 03 §4.16）。

### 第 6 步 · 回填出链（双向，不做就是孤岛）

**向外出链**（concept → 别的层）：

| 提到什么 | 出链到 | 现状 |
|---|---|---|
| 具体工具 / 产品 / 机构 | `entities/` | **0 条**——RAG 页列了 FAISS、Milvus、Qdrant、ES、Pinecone，文档解析页列了 MinerU、PaddleOCR-VL，全无链接 |
| 两个方案的取舍 | `comparisons/` | 待补 |
| 某个项目怎么落地 | `solutions/` | 待补 |

```bash
# 列出正文提到却没出链的具名对象
python3 skills/wiki-concept-page/scripts/verify_concept_page.py --links
```

指向尚未创建的页面时标 `[待创建: [[名称]]]`，**不要留死链也不要不写**。

**向内被引用**：`sources/` 的「关键概念」节、`entities/` 的「相关」、`solutions/` 用到的原理骨架、`map/` 的导航。

### 第 7 步 · 查重复定义（改多页时跑）

```bash
python3 skills/wiki-concept-page/scripts/verify_concept_page.py --dup
```

同一机制在多页被展开时，**留一处、其余改一句 + 出链**（03 §4.13）。不删内容，是**把展开点收敛到一页**。

## 硬规则速查

| 规则 | 判据 |
|---|---|
| 可复用优先于齐全 | 只有能被另一个项目复用的内容才进 concept |
| 一个函数做一件事 | 独立可答 / 独立边界 / 独立引用，任一通过即独立成页 |
| 三节必齐 | 是什么（签名）＋ 怎么运作（实现）＋ 适用场景与失效边界（前置条件与异常） |
| 失效边界带数字与口径 | 「约 70% 多 + 无分母无测量方法」；不能只写「数字不可信」 |
| 来源必须可见 | 行内 `〔〕`，多源页带来源短名；不用 HTML 注释 |
| 来源表只登记不综合 | 「各来源是否一致」属于 `synthesis/` |
| 新来源合并不新开节 | 合并进「来源与证据」表 + 更新正文 |
| 归一机制一处展开 | 父子页写一句 + 出链 |
| 提到工具就出链 | 首次出现处 → entity |
| 素材的判断要保留 | 讲师说「必须上人工」是素材内容，要写；「它很好用」是你的评价，不写 |

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 从「素材讲了什么」往下切 | 写出结构齐全、闭卷答不出的页 | 第 2 步「从业务问题反推」 |
| 用出现频次当准入判据 | 讲透的原理反而不建页 | 判据是「能否复用」 |
| 「怎么运作」写成名词列举 | 读者照着重跑不了 | 每步写输入 → 处理 → 输出 |
| 有数字只写「不可信」 | 读者既不知量级也不知该不该信 | 数字 + 口径一起留（脚本会 WARN） |
| 用 HTML 注释标来源 | 阅读视图不可见，等于没标 | 行内 `〔〕`（脚本会 FAIL） |
| 新来源进来新开一节 | 同一功能两套结构 | 合并进来源表（脚本会 WARN） |
| 父子页重复展开 | 三处维护、互相矛盾 | 父页一句 + 出链（`--dup` 会报） |
| 提到工具不出链 | 标准库不连符号表 | `--links` 会列出漏失项 |
| 把项目编排决策写成 concept | 换个项目就不成立 | 进 `solutions/` |
| 把工具版本特性写进 concept | 概念页跟着产品过时 | 进 `entities/` |
| 填 `author: llm` / `created` / `updated` | 字段口径分裂 | frontmatter 以 03 §2 为准（脚本会 FAIL） |
| 不查重就新建 | `RAG.md` / `检索增强.md` 并存 | 先 `--links` 查名称清单 |

## 边界

| 你想写的 | 该去哪 |
|---|---|
| 这个原理是什么、怎么运作、怎么用 | **这里** |
| 某个具体工具 / 产品 | `entities/` |
| A 和 B 两个概念差在哪 | `comparisons/` |
| 某类项目如何设计端到端方案 | `solutions/` |
| 素材原文说了什么 | `sources/` |
| 我对这个原理的判断 | `wiki/notes/`（判断型） |
| 为达成某目标，按什么顺序协调这些机制 | `wiki/notes/`（方法论型）——跨概念编排，属枢纽页 |
| 多份素材合起来能得出什么 | `synthesis/` |

## 检索策略

| 场景 | 行为 |
|---|---|
| 「XX 是什么」「XX 怎么运作」 | 命中 `concepts/` |
| 「XX 该怎么做」 | 命中 `concepts/`（`concept_type: 方法`） |
| 「这个数字什么意思」 | 命中 `concepts/`（`concept_type: 指标`）→ 下钻 source 核口径 |
| 「用哪个工具做 XX」 | `entities/` + `comparisons/` |
| 关联计算 | concept ↔ concept 是主干；concept ↔ entity 出链**不计关联边** |

## 已知限制（必须告诉使用者）

1. **脚本查不出「粒度切错」。** `--dup` 能发现同一机制在多页被展开，但「这个机制该不该独立成页」只能人工按 §4.13 的三个测试判。
2. **脚本查不出「闭卷答不出」。** §0 的完备性标准是语义判断——拿业务问题闭卷答一遍，只能人工做。
3. **「失效边界有数字」是启发式。** 脚本按数字/百分比/金额/时间正则判断，**有数字不等于数字有用**（「约 70% 多」合格，「第 3 步」这种序号也会被算进去）。判定为 WARN 不是 FAIL，需要人看一眼。
4. **多源页的来源短名无法自动核验。** 脚本只能查「有没有带短名」，查不出短名与 source 页是否真对得上。
5. **`--links` 的具名对象识别沿用 entity skill 的通道**（拉丁词 + 中文词表兜底）。**中文无后缀专名（豆包、元宝这类）扫不出来**，需要人工扫正文。
