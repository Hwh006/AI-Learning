# solution 项目设计方案页（参考实现）

## 定位与页型边界

solution 页 = **wiki 的参考实现**。

素材里讲过的那个实例——场景、角色、痛点、流程、动作、功能点、异常——被解析成一份**可参照的方案**。它**不写**：这份素材说了什么（→ `sources/`）、这件事一般怎么做（→ `concepts/`）、该选哪个（→ `comparisons/`）、跨源归纳出的新结论（→ `synthesis/`）。

写得好不好，只看一条（09 §0 的完备性标准）：

> **解析闭合**：素材讲过的那个实例，被完整解析成一份可参照的方案。
> **可重建** —— 不翻素材，只看本页，能否把这个实例讲全？
> **可参照** —— 提炼出的做法，能否用于同类设计？
> **可追寻** —— 每个说法指得到素材位置？待确认项能直接问出口？

**最重要的判别句**：正文里能不能指到那个**具体实例**（哪次课、哪个作者、哪家公司的那套流程）？

> **指不到，就是方法论，归 concept 不归本页。**

现库里 `业务单据建模与状态设计` 就止步于这一句：它给的是「建模七步 + 检查表」，指不到任何具体实例，而 concept 页 `订单履约与业务单据关系` 已在讲同一件事的不同侧面。

**职责分工**：`index.md` 统一定义页型职责、适用条件和边界；本 Skill 定义本页型的字段、章节、执行步骤与校验。分类冲突按 `index.md` 处理，写作结构以本 Skill 为准，并同步修正不一致内容。

**标签自检**：写入或修改 Wiki 页时，按项目 `AGENTS.md` 的标签规则，从本页主旨、反复讨论的对象与关键机制提取具体检索词；每个主题标签须能在正文找到依据。素材类型标签另保留，不能单独充当主题标签。

| 本 skill 自带 | 什么时候看 |
|---|---|
| `scripts/verify_solution_page.py` | 每写完一页必跑，见第 6 步 |

## 触发条件

### 应调用

- 素材里出现**成型的项目实例**：有具体业务场景、参与角色、流程步骤，且讨论了字段、状态或系统协作中的至少一项
- 素材里出现**某类系统的完整业务链路**：从触发到结束能讲成一串动作
- 素材讲的是**某个作者做过的项目**（课程案例、视频里作者讲述的案例），给的是做法而不是只给结论
- 排查方案页写成了概念摘要（通篇「一般应该怎么做」）、source 摘要（按素材顺序罗列）或实施记录（出现客户名、排期、报价）
- 排查骨架问题：十二节平铺没分四段、节跨段摆放、段内全空还留段标题、必写节拿 concept 的通用原理凑
- 排查「待确认清单」写成「由业务确认」「视情况而定」
- 反扫尚未建页的业务主题（`--scan` 直接给清单）

### 不应调用

- 只是讨论、回答、总结 → 不写页
- **只有通用步骤清单、指不到具体实例** → `concepts/`（跑 §7.1 的 Q2）
- 只有一个功能点或一个页面的描述 → `concepts/`，或并入已有方案页的「关键动作与功能点」节
- 是课程对某类系统的**建议**，没有实例支撑 → concept 的「怎么用」节
- **具体客户的上线实施方案**（排期、报价、客户名）→ **不入库**
- 两个候选的选型 → `comparisons/`
- 跨源归纳出的结论 → `synthesis/`

## 输入契约

### 必填

- **工作目录**：项目根。脚本路径（`skills/wiki-solution-page/…`）、素材路径（`raw/…`）、页面路径（`wiki/solutions/…`）都相对它，命令请在这个目录下执行。
- **主题名**：业务模块级（会员管理、订单履约与售后），不取公司名、不取「哪次课讲的」。
- **来源范围**：涉及这个主题的 source 页。

### 选填

- 是否含外部来源（影响 `case_origin` 与正文的 `外·` 标注）

## 四段阅读骨架 + 逐节档位

页面是**两层**：`##` 四个**阅读环节**（读者按顺序读完一页）＋ `###` 十二个**内容要素**（维度一个不丢）。**段名、节名、顺序、节与段的归属全部固定。**

```markdown
# {业务主题}设计方案

> {一句话：这个主题的方案，在什么情况下解决什么问题}

## 一、这是什么方案
### 业务场景与痛点
### 核心角色与职责

## 二、方案怎么运转
### 业务流程与状态
### 关键动作与功能点
### 数据对象与字段

## 三、边界与保障
### 异常与逆向流程
### 系统协作与边界
### 〔AI 能力与评估〕
### 指标与验证

## 四、怎么落地、还缺什么
### 版本拆分与取舍
### 待确认清单
### 相关
```

**每段回答什么**（读者读完该能说出）：

| 段 | 回答 | 读完该能说出 |
|---|---|---|
| 一、这是什么方案 | 什么业务、什么阶段、谁参与 | 为谁解决什么问题 |
| 二、方案怎么运转 | 一步步怎么走、谁在何时改什么、落到哪些字段 | 照着能画出主流程 |
| 三、边界与保障 | 出事怎么退、跟谁对接、怎么知道成了 | 这套东西的边界在哪 |
| 四、怎么落地、还缺什么 | 一期做到哪、还有什么必须问清 | 下一步做什么、该去问谁 |

### 缺料档位（动笔前先看）

| 档位 | 含义 | 缺料时怎么办 |
|---|---|---|
| **必写** | 缺了它，这页就不是方案（或该降级 concept） | 回 raw 找；找不到 → 这个实例撑不起 solution 页，重过闸门 |
| **有料就写** | 素材常不交代，有则写 | 回 raw 找；找不到且属「必须问清才能设计」→ 进待确认清单；否则整节删 |
| **可缺** | 有没有都不影响方案成立 | 按 09 §4.0 处理，多数情况整节删 |
| **条件节** | 方案里有环节由模型承担才写 | 见本节末 |

**段的删法**：段内节**全部没料** → 整段删，不留段标题；但**含必写节的段不能整段删**——那说明缺的是方案本身，该回去过四个闸门，而不是删段。

**「必写」不等于「硬凑」**：必写节内容单薄时宁可写短，也不要拿 concept 页的通用原理来填。

### 十二节速查（含档位）

| # | 节 | 段 | 档位 | 一句话判据 |
|---|---|---|---|---|
| — | （`> ` 引文） | — | 必写 | 这个主题的方案在什么情况下解决什么问题 |
| 1 | 业务场景与痛点 | 一 | 有料就写 | 先说适用条件，再说实例里的具体痛点（可观察的表现，不写「效率低」） |
| 2 | 核心角色与职责 | 一 | 有料就写 | 表格；角色名用素材原话，不统一成「用户」「管理员」 |
| 3 | 业务流程与状态 | 二 | **必写** | 每步写清输入、动作、输出；状态名用原话，区分「拒绝结束」与「驳回待改」 |
| 4 | 关键动作与功能点 | 二 | **必写** | 表格；动作是业务方的，功能是系统的，**分两列** |
| 5 | 数据对象与字段 | 二 | 有料就写 | 对象表 + 关系基数；字段具体到能核对，禁「等字段」 |
| 6 | 异常与逆向流程 | 三 | 有料就写 | 触发条件 + 处理路径 + 终态 |
| 7 | 系统协作与边界 | 三 | 有料就写 | 各系统负责什么 + 数据方向；素材没给的接口契约进待确认，不用工程经验补成事实 |
| 8 | 〔AI 能力与评估〕 | 三 | 条件节 | 方案里有环节由模型承担时**必写**；四件事分开：模型承担什么 / 数据与知识准备 / 效果指标与评测集 / 人机兜底 |
| 9 | 指标与验证 | 三 | 有料就写 | 每个指标带口径、分母、来源；素材数字标「课堂假设」还是「实测」 |
| 10 | 版本拆分与取舍 | 四 | 可缺 | 一期 / 可人工 / 迭代，**保留取舍的理由** |
| 11 | 待确认清单 ★ | 四 | **必写** | **每条写成能直接问出口的问句**，含疑问点 + 具体对象 |
| 12 | 相关 | 四 | **必写** | 至少一条 concept 出链；标题不得与 concept 页同名 |

（表内 # 是速查序号，不是页面里的编号——页面里节名**不带编号**，只有四段带「一、二、三、四」。）

**条件节启用判据**：正文里出现大模型 / RAG / 意图识别 / 准确率 / 召回 / 模型 / Agent / 智能客服 / 知识问答 / 质检 这类内容 → 启用；纯业务系统方案**不要为它凑内容**。

**Q3 与档位不是一回事**：判页闸门 Q3（数据对象 / 系统协作 / 版本取舍 / 指标至少撑起两项）是**建页门槛**；档位是**页内缺料处理**。过了闸门的实例，某一节没料就按档位处理，不因此推翻建页决定。

## 执行流程

### 第 1 步 · 定主题

从素材里那个成型实例提取**业务主题名**：

| 取什么 | 不取什么 |
|---|---|
| 业务模块：会员管理、订单履约与售后、线索到成交 | 公司名：XX 公司的 CRM |
| 系统模块：质检、知识问答、ChatBI | 素材名：第五天课程讲的 |
| | 事件名：那次讨论的 |

### 第 2 步 · 查重

```bash
python3 skills/wiki-solution-page/scripts/verify_solution_page.py --dup
```

- 已存在同主题页 → **合并**进已有页，两份来源的标注都保留，不新建
- 标题与某个 concept 页同名 → **必须改名**（同名会造成同一主题两个权威）
- 主题与已有页重叠但不同 → 出链互指，不复制内容

### 第 3 步 · 过判别闸门

按顺序问四个问题，**任一步给出「否」就停下**：

```
Q1  素材里讲的是一个具体实例吗（有场景、角色、流程）？
    └─ 否 → 通用方法 → concepts/
Q2  这个实例指向某个可辨认的讲述（哪节课、哪个作者、哪家公司）？
    └─ 否 → 方法论拼装 → concepts/
Q3  能撑起「数据对象 / 系统协作 / 版本取舍 / 指标」中的至少两项吗？
    └─ 否 → 是一个功能点 → 并入已有方案页对应节，或 concepts/
Q4  是具体客户的上线实施方案吗（排期、报价、客户名）？
    └─ 是 → 实施记录 → 不入库
```

### 第 4 步 · 取料

```bash
# 4a. 从 source 页确定范围（哪些 source 涉及这个主题）
grep -l "关键词" wiki/sources/*.md

# 4b. 回 raw 取准位置——用 01 的 --locate，不要重新实现
python3 skills/wiki-source-page/scripts/verify_source_page.py \
    --raw "raw/record_cleaned_markdown/X.md" --locate "原文短摘录"
```

**两个坑**：

- ⚠️ **智能纪要类 source 页没有段号系统**，位置必须回 raw 取。source 页自己写的位置若是「在对应原文中全文检索该摘录」，那是**占位符**，不能直接抄进方案页。
- ⚠️ source 页薄（有的只有 33 行、3 条核心观点）时，方案页的细节必须回 raw 补——但**仍要经过 source 页登记**，不能绕过。

### 第 5 步 · 写页

**先搭骨架，再填内容**：写四个 `##` 段 → 在段内填 `###` 十二节。三条纪律：

1. **先看档位再动笔**（见上表）：必写节必须有内容；「有料就写 / 可缺」的节缺料时按 09 §4.0 处理，别硬写。
2. **记录与提炼分开**：实例事实带 `〔〕` 位置标注；提炼出的做法以 `**提炼**：` 另起一句，说明依据。**禁止**把提炼混进事实句里——那会让读者以为素材这么说过。
3. **段内节全删则整段删**；含必写节的段不能整段删——那缺的是方案本身，回去过闸门。

### 第 6 步 · 自检

```bash
python3 skills/wiki-solution-page/scripts/verify_solution_page.py --page "wiki/solutions/X设计方案.md"
```

脚本机检：frontmatter 必填与废弃字段 / `case_origin` 与 `外·` 标注是否对应 / **四段骨架与段内十二节的顺序** / **缺料档位（必写节缺失即 FAIL；旧结构页报 WARN「待迁移」）** / 条件节启用判据（正文有模型内容却没启用，或启用了却没模型内容）/ **待确认清单每条是否可问出口** / 「提炼」标记 / `〔〕` 位置标注覆盖率 / 出链与死链 / 与 concept 页标题撞名。

**脚本验不了最后一问**——「这个实例解析得全不全」。人工做：**把页面交给一个没读过素材的人，看他能不能把这个例子复述出来。** 复述不出 → 缺节或该节写得太浅。

### 第 7 步 · 收尾

- 核对方案页的 `title`、`type`、`tags`、`sources`，确保 `tools/wiki_lookup.py` 能定位；不维护逐页目录
- 源清单不一致、主题重叠的情况登记到 `review.md`

## 自检脚本

```bash
PY=python3

# 单页自检
$PY skills/wiki-solution-page/scripts/verify_solution_page.py --page "wiki/solutions/X设计方案.md"

# 全库体检 + FAIL 聚类
$PY skills/wiki-solution-page/scripts/verify_solution_page.py --all

# 与 concept 页标题撞名 + 源清单重合检测
$PY skills/wiki-solution-page/scripts/verify_solution_page.py --dup

# 反扫未建页的业务主题候选
$PY skills/wiki-solution-page/scripts/verify_solution_page.py --scan
```

## 已知限制

- **四段骨架有迁移期**：2026-09-25 之前建的 solution 页仍是十二节平铺，脚本对它们报 WARN「未按四段骨架，待迁移」，不报 FAIL；新写的页按四段要求。存量迁移清单见 `review.md`。
- **`--scan` 是启发式**：按业务域词表（CRM / 会员 / 订单 / 客服 / 质检 / 知识库 / ChatBI / 法律…）扫 source 与 concept 页，再减去已建 solution 覆盖的主题。词表外的领域扫不出来，需人工扫正文。
- **「可重建」不可机检**：脚本只能查骨架齐不齐、标注在不在；「这个例子讲全了没有」只能人工复述验证。
- **提炼标记的判定是启发式的**：脚本统计 `**提炼**：` 出现次数，不判断提炼得对不对。
- **来源类型标注靠短名前缀**：`外·` 前缀是约定，脚本只能提醒缺失，无法判断某个标注该不该加前缀。
- **`--dup` 的源清单重合检测有误报**：同一主题的 concept 页与 solution 页共享来源是正常的，重合度高只提示人工看一眼，不直接判错。
