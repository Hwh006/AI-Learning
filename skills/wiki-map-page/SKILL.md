# Map Wiki：将已有知识组织成知识体系

## 目标与产物

将库内碎片化知识抽象为“领域 → 专题 → 子知识点”，让读者能够理解知识的位置、查看相关主题，并进入已有 Wiki 阅读具体内容。

每个领域使用一篇 map Wiki，例如：

- wiki/map/AI.md
- wiki/map/供应链.md

专题和子知识点使用该页内的多级标题展开，不另外为每个专题创建地图文件。

已有领域页优先更新。涉及多个领域时，可通过总入口链接各领域页；总入口不重复展开全部知识点。

页型职责与写入边界以项目根目录 index.md 为准。

## 适用范围

用户要求以下工作时使用：

- 将现有知识库整理为知识地图。
- 梳理某个领域的知识体系。
- 将新增 Wiki 挂入已有地图。
- 调整地图的领域归属、专题层级或横向关系。

用户只要求讨论结构或提供草稿时，先交付相应内容，不直接修改正式文件。

已授权的 Wiki 生成或改写完成后，由 [Wiki生成后同步Map工作流](../wiki-generation-map-sync/SKILL.md) 自动接续增量维护；该工作流定义交接、批次与完成条件，本 Skill 定义地图的组织和写法。

## 收录对象

默认组织可检索的 concept、note、solution、comparison、entity、synthesis 和 query 页面。

默认不收录：

- source 页面。
- raw 原始材料、图片等资源文件。
- 个人 memory 和项目事实文档。
- 历史归档、下划线目录和 searchable: false 页面。

具体范围以用户当前要求为准。不要把某次盘点的领域数量、页面数量或专题目录固化为规则。

## 核心组织方式

### 向上：确定知识归属

得到一个知识点后，先判断：

1. 它属于哪个更高维度的领域，例如 AI、供应链、金融。
2. 在该领域内，它属于哪个专题。
3. 它是独立专题，还是某个专题的子知识点。

根据页面主体内容判断，不以文件夹、工具品牌、来源或孤立关键词代替语义判断。

例如：

AI → RAG → 分块

“分块”属于 RAG 的下层知识点；不能因为它能独立解释，就自动把它提升为与 RAG 并列的领域专题。

### 横向：寻找同层主题与关联

在确定所属层级后，寻找：

- 同一上位主题下的并列知识点。
- 可以比较、组合或互相补充的能力。
- 与其他专题共享的能力。
- 跨领域的业务衔接。

例如：

- AI 下，RAG、Agent、Skill、Harness、记忆、上下文和评测可以作为专题入口。
- RAG 下，解析、分块、元数据、检索和重排可以作为子知识点。
- RAG 可以横向关联评测，说明读者在哪里继续查看检索与生成质量验证。

关联处简短说明关系或阅读目的。只有相同标签、相同来源或名称相似，不足以建立关联。

不要将并列主题写成必须顺序执行的步骤，也不要把共享能力强行归为某个专题专有的下级。

### 纵向：拆出更具体的知识点

从专题继续向下拆分，直到能够挂载已有 Wiki。

例如：

- AI
  - RAG
    - 解析
    - 分块
      - 固定长度分块
      - 语义分块
      - 父子级分块
    - 元数据
    - 检索
      - 语义检索
      - 关键词检索
      - 混合召回
    - Rerank

层级深度由知识关系决定，不固定为两层或三层。

一个已有页面涵盖多个子知识点时，可以在相应位置复用链接，不要求为每个子知识点新增页面。

## 执行流程

### 1. 确定整理范围

结合用户要求判断是全库整理、指定领域整理，还是增量更新。

检查已有 map 页，复用已确认的领域名称、结构和入口。当前要求覆盖已有结构时，按当前要求调整。

### 2. 盘点已有知识

先读取标题、标签等元数据形成候选，再核读支撑分类和关联判断的必要正文。

项目提供 tools/wiki_lookup.py 时，按项目检索 Workflow 定位候选。全库整理时建立范围内页面清单，用于后续检查遗漏。

关键词匹配可以辅助筛选，不能直接决定最终归属。

### 3. 构建领域内的知识骨架

先向上确定领域，再在领域内组织专题和子知识点，同时检查横向关联。

对每个分支确认：

- 上位概念是什么。
- 与同层分支有什么区别。
- 下层还能拆出哪些已有知识。
- 对应哪些真实存在的 Wiki 页面。

领域和专题来自现有内容的抽象。不要为了构成完整百科而预填没有内容支撑的目录。

### 4. 在领域页内编排

使用编号标题表示层级：

- 一级专题：1、2、3。
- 子知识点：1.1、1.2、1.3。
- 需要继续拆分时：1.2.1、1.2.2。

页面开头提供页内目录。

每个知识点下挂载对应的已有 Wiki 链接；必要时增加一句范围说明。专题之间通过页内标题链接关联，跨领域通过对应领域页或标题链接关联。

使用项目约定的 Obsidian 双括号链接。目标不唯一时使用项目内完整路径，标题锚点必须真实存在。

### 5. 更新与维护

新增知识优先挂入已有分支；只有出现实质不同的知识主题时才增加分支。

更新时：

- 保留仍然有效的知识链接与关系。
- 页面改名、合并或停用后，同步修正受影响入口。
- 调整标题编号后，修正相关页内和跨页锚点。
- 同一知识页可被多个相关分支引用，不要求互斥分类。
- 重构旧地图时，先确认链接已迁移，再清理本次范围内的过时地图文件。

整理地图不自动授权重写、合并或删除原知识页。

## 页面结构示例

以下仅展示组织方式，实际专题和链接根据现有知识生成：

```markdown
---
type: map
title: AI
tags: [AI, 知识地图]
searchable: true
---

# AI

## 目录

- [[#1. RAG|1. RAG]]
  - [[#1.1 解析|1.1 解析]]
  - [[#1.2 分块|1.2 分块]]
  - [[#1.3 元数据|1.3 元数据]]
- [[#2. Agent|2. Agent]]

## 1. RAG

横向关联：[[#2. Agent|Agent]]，查看知识检索如何与任务执行衔接。

### 1.1 解析

挂载已有的解析、OCR 和文档结构相关 Wiki。

### 1.2 分块

挂载已有的分块方法、取舍和实践 Wiki。

### 1.3 元数据

挂载已有的元数据、过滤和溯源相关 Wiki。

## 2. Agent

继续按该专题已有知识展开子知识点。
```

示例中的说明文字在正式产物中应替换为真实链接；不保留虚构链接或占位内容。

## 内容边界

地图主要保存知识结构、简短范围说明、关联关系与已有页面链接。

- 不复制知识页正文。
- 不补写未经授权的新知识或综合结论。
- 不将地图的分类编排当作事实来源。
- 不因地图收录而改变原页的状态或置信度。
- 没有对应内容的知识缺口可简短注明，不创建空页面，也不伪装成已覆盖。

## 完成检查

交付前检查：

1. 每个领域是否使用一篇 Wiki 承载专题与子知识点。
2. 上下层关系是否成立，同层主题是否具有可比较的粒度。
3. 横向关联是否说明了实际关系或阅读目的。
4. 知识页链接与标题锚点是否有效。
5. 是否排除了本次范围之外的页面，尤其是 source。
6. 全量整理时，范围内页面是否均能从地图进入；重复引用按同一页面去重计算覆盖。
7. 是否保留了原知识页内容，并清理本次不再需要的临时文件。

交付实际生成或更新的领域 Wiki 入口，简要说明范围和必要缺口，不用文件数量代替整理效果。
