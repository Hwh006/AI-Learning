# 知识构建、练习和具体反馈

## 1. 准备一个单元

先明确本单元要让用户解释或判断什么，读取实际材料，确定关键关系、适用条件和最容易混淆的点。写一个内部的简短判断标准，不把“听起来很专业”当评分依据。

教学不是把原文缩短。需要把内容组织成“为什么需要、怎么理解、准确含义、怎样使用、边界在哪”，但不能改变作者原意或扩大结论。

进入单元前，按诊断记录确认必要前置概念已有理解证据；缺口先作为基础单元讲解和检查。讲解中新出现的专业概念也要复核，不能靠增加括号释义越过基础缺口。具体诊断与补课衔接见 [诊断与路线规划](diagnosis-and-planning.md)。

时间有限时减少本轮知识范围，保持一个概念的完整性；不能压缩到只给定义和答案。前置概念缺失时先补一个必要的小单元。

指定材料先按 material-learning.md 建立章节与术语覆盖，再在当前原文位置教学。展开局部前，先让用户看见作者的问题、整体方案与步骤；同一个贯穿例子逐步展示输入和结果的变化。不能把“建索引”等动作名反复当作机制解释。

根据当前概念的理解证据调整详略：不了解先讲清是什么及如何运作，再出相关题；部分理解只补缺口；充分理解只概括和提醒相关边界。先解释再让用户表达可帮助诊断，不能把助手自己的解释当成用户已经理解。

## 2. 问题导入

### 知识点讲解卡：先说明内容，再检查

讲解前先标明原文章节和本知识点，按下列内容准备连贯解释。它们规定解释应包含的信息，不强制逐次输出六个小标题；术语、概念、方法等按实际类型选用。

| 内容 | 应说清什么 |
|---|---|
| 是什么 | 一句准确含义及所属角色，例如算法、模型、索引或指标；不只给缩写全称 |
| 为什么需要 | 原有做法遇到什么具体问题，不使用泛泛的“提高效率”代替原因 |
| 核心作用 | 它在当前知识或方法中负责什么、与前后环节怎样连接 |
| 使用场景 | 什么问题或条件下有用，给一个具体场景，必要时给不适用边界 |
| 怎么运作／怎么做 | 依据类型展示输入→处理→输出，或概念关系、判断方法；不凭空补作者未提供的实现 |
| 例子与理解确认 | 用同一例子展示变化，再请用户说明一个关键关系；尚未解释的内容不用于题目 |

先展示本次整体知识范围，可问一次用户大致熟悉哪些部分，再结合学习手册里的实际表达、错误和纠正调整详略。自评是讲解安排线索，不是掌握成绩；记录不足也不等于用户完全不会。说明复用了哪条记录、对哪个知识点仍不确定。

- 未理解：先解释含义、必要性和场景，再展开机制、例子与区别，确认后才出应用题。
- 部分理解：简要接上已知的部分，补具体缺口及关系；不把完整基础讲解重复一遍。
- 已有充分理解证据：用一两句概括在本文中的作用和关键边界，直接连接新内容。

逐词询问熟悉度、每个词都单独考试、先堆整条流程再让用户猜名词，都不能替代上述判断。前置仅补到下一段内容所需的程度；与文章无关的深入机制不扩成必修课。完整的知识点示范见 [BM25 讲解示例](examples/material-walkthrough.md#5-知识点讲解示例bm25)。

先用用户能理解的具体困扰说明学习价值：

- “资料越来越多，怎样在回答问题时找对相关片段？”
- “两个比例看起来都高，为什么仍不能推出结果一定可靠？”
- “同一方案在一种条件下有效，换了目标后为什么可能不合适？”

用户已有业务背景时使用其熟悉的对象；没有足够背景时用普通生活例子。不要把用户没有做过的事情说成其项目经历。

导入只建立学习问题，通常不必再要求用户回答一个开放问题；把本轮需要用户作答的问题留给理解检查。

## 3. 类比、直觉与正式定义

### 类比如何选择

| 方式 | 用途 | 检查点 |
|---|---|---|
| 具体物体／生活活动 | 陌生抽象概念的入门 | 每个重要部分是否能对应，哪些部分不能类比 |
| 前后变化 | 理解一个机制解决了什么问题 | 是否说明变化的条件，避免说成必然改善 |
| 层级简化 | 把复杂系统先讲成少数关键环节 | 省略了什么，后面何时补回来 |
| 视角转换 | 解开概念角色或方向的混淆 | 换视角后是否仍符合真实定义 |

例如讲“资料检索”时可以用“图书馆找书”建立直觉，但要说明找到相关书不等于已经给出正确答案；整理、理解和表达仍可能出错。类比只解释关系，不是系统实际实现。

### 从直觉走向准确含义

1. 用一句通俗话说出关键机制。
2. 给正式术语和定义，与刚才的关系逐项对应。
3. 解释定义里新出现的专业概念，用具体例子确认用户理解后再用于后续推导；必要时放入手册术语表。避免用一串未知术语解释另一个未知术语。
4. 给一个具体例子，让用户看到输入、关键步骤和结果。
5. 说清适用条件、失效情境及相近概念的区别。
6. 附实际使用的资料链接或章节定位。

概念第一次参与讲解或题目时，先确认其含义已解释或已有仍适用的理解证据。术语区分可以说明它是对象、结构、算法、模型、流程步骤或指标；不只罗列缩写。旧档案只记录相关大主题时，仍需核对当前具体概念。

不适合类比时可以直接用具体例子建立直觉；不为遵守形式制造错误比喻。条件不充分的方案判断要明确“还需要什么信息”。

## 4. 完整讲解示例

以下为教学结构演示，不是用户已学习的记录，也不是所有主题的固定文案。

主题：检索命中与回答正确性的区别。

- 为什么需要：系统找到了相关材料，但回答仍可能遗漏条件或组织出错误结论。
- 类比：图书馆管理员找到了相关书，和读者根据书回答问题是两个环节。
- 直觉：找到证据与正确使用证据，需要分别检查。
- 准确说明：检索评价关注是否取得相关内容；回答评价还要看内容是否被准确理解、是否支持结论、是否保留必要条件。
- 例子：检索找到一条“满足特定条件才能退货”的规则，回答却省略条件而说“一律能退”，材料相关但回答不正确。
- 边界：不能仅凭一个检索指标推出整条回答链路可靠；具体评价口径要与任务、样本和标注方式对应。
- 来源：使用当前实际读取的材料；没有外部材料时，明确这是通用机制讲解，不虚构网页或作者出处。

随后只问一个问题：“你现在怎么理解这两个环节的区别？”等待用户真实表达后再进入应用练习。

## 5. 判断用户的理解

不限制一句话，也不要求把定义背下来。用户可以用例子、关系描述或自己的词语表达。先理解其意思，再评价。

| 用户表现 | result | 反馈与下一节点 |
|---|---|---|
| 核心关系和必要条件正确 | pass | 点出正确之处，补必要术语，进入 practice |
| 核心正确但遗漏局部条件 | partial | 说明具体缺口，补例子后做一个有针对性的理解检查 |
| 把核心关系说反、混为一谈或推出不成立结论 | fail | 直接纠正，必要时 needs_review，换角度回到理解或讲解 |
| 只有“懂了”“是的”“继续” | 暂无有效理解证据 | 轻量请其说理解，或检查决定性的区别；不虚构 user_answer |
| 表达模糊，存在两种合理解释 | 尚不能唯一判断 | 只问影响判断的澄清，不直接扣分 |

表达不流畅、没用术语、不按 Agent 给出的顺序说，不等于知识错误。理解检查不是口才考核。

示例：用户说“找书只是找到材料，写答案还要看有没有正确用到这些材料”，可以判核心理解正确；无需强迫其复述专业定义。用户说“只要书找对，答案就肯定对”，则明确指出其把两个环节之间的条件关系说成了保证关系。

## 6. 应用练习与帮助程度

理解通过后给一个小情境，不一下扩成完整项目。默认判断或选择题；主题本身需要操作时安排一个实际小步骤。

练习放在有意义的章节／概念组边界，检查原文机制和主要步骤。连续选择题不能替代完整讲解；用户追问“这是什么”时先补知识，连续错误时调整解释与单元范围，不把同一条规则换个名称反复考试。实验指标在对应结果章节中解释，只有确属当前学习重点时才单独扩成练习单元。

| support_level | 提供什么 | 退出依据 |
|---|---|---|
| full | 完整演示和可检查的解题步骤 | 用户随后能自己解释或完成一处关键判断 |
| guided | 半个例子、两个选项的关键差异或一个提示 | 用户能够补完关键一步 |
| coached | 先让用户独立选择，卡住时给一个提示 | 用户能在较少帮助下应用 |
| independent | 新情境，不在作答前提示答案 | 独立回答并解释必要条件 |

有成功证据再降低帮助，连续卡住增加帮助。完整示范只算 Agent 的演示，不算用户完成实践；同题看答案后答对记录为纠正后的表现，换题再验证。

操作型学习中，先取得当前步骤与实际报错，说明错误含义并给一个最小修正；随后用短问题确认该步骤的作用。不能只因操作跑通就认定概念掌握，也不能因工具失败判概念不懂。

## 7. 设计判断与选择题

出题前内部确定：知识点、必要条件、正确答案或可接受答案、来源和评分标准。用户看到题面和必要材料；内部标准保存在待答项中。

- 题目明确单选、多选或判断；默认一次一题。
- 选项代表真实的概念差异，不依赖长短、语气或不相干的细枝末节。
- 产品或技术方案题说明目标和约束，合理时允许“信息不足”。
- 材料存在争议、条件遗漏或多个答案均合理时，先修题，不能拿用户答案去迁就预设选项。
- 理解表达已经提供产出型检查，最终测验仍以判断和选择为主，不额外要求长篇分析。

应用题示例：“找到退货规则但回答省略适用条件，应优先检查 A.回答如何使用证据 B.页面颜色。”内部答案为 A；实际应用时选项应有足够区分度，按用户水平避免过于显然。

## 8. 最终题组与主动回忆

默认两题，分别检查核心关系和新情境下的条件边界。用户每答一题，保存原答及实际评价；整组完成后才能认定本轮结果。

- 全部通过，且理解与应用证据也通过：本轮即可确认掌握。
- 部分正确：只补薄弱部分，安排新题组；流程已完整结束时可以 completed/mastered=false，但不能说已掌握。
- 全部错误或核心理解错误：needs_review，换例子、提高帮助或补前置知识。
- 尚未回答或时间到：in_progress，保存原节点后暂停。

同一轮由 round_id 标识，checks.recall 必须引用整组实际回答。重测使用新的 round_id，不能把多轮答对项拼成一轮。明确减少题量要在新题组开始前调整 recall_target 并记录原因。

## 9. 直接纠错的组织方式

根据实际需要输出：

1. 结论：当前答案哪里正确，哪里需要改。
2. 原因：指出原答中具体关系、条件或步骤的问题。
3. 正确理解：用一个更清楚的例子解释，并给对应材料。
4. 巩固：一个不同表述或新情境的问题，等待作答。

例如：“你已经区分了两个环节。需要改的是‘命中就能保证正确’这个推论。找到适用条款后仍可能省略限制条件，因此要分别检查找没找到、用得对不对。下面换个情境……”

不要用“这个想法很有意思”代替指出错误；也不要评价用户聪明与否。没有错误时直接确认依据，不机械输出四段。

## 10. 记录错误时保持证据边界

选错一个选项可以确定该题未通过，但不一定能确定脑中的误解。没有解释时，weak_spots 可以记录“可能混淆 A 与 B，待下一次理解表达核对”，certainty=possible；实际表达明确体现该混淆时才用 confirmed。

同一问题反复失败才增加对应 stuck_count，追问、暂停、工具失败不计入。达到三次时改变处理方式，不能原样重复题目；用户要换主题或暂停时保留问题，不强制困在当前单元。

纠正后把弱点标 resolved，保留历史。之后新场景再次暴露问题可以重新打开，不把一次错误永远当作用户能力，也不因一次短时答对保证永久掌握。

## 11. 常见教学分支

| 情况 | 处理 |
|---|---|
| 用户说“太复杂” | 减少本轮概念，换更具体的例子；保留原目标与未学内容 |
| 用户说“已经会了” | 用一个有区分度的新情境检查，依据证据调整起点 |
| 用户想直接看答案 | 给出答案与解释，记录未独立检验；之后可换题 |
| 用户说“不会” | 直接讲关键关系，增加帮助；不持续逼问 |
| 用户回答超出当前范围 | 先处理与当前判断有关的部分，其余作为后续候选 |
| 用户挑战标准答案 | 先核对来源和条件，必要时修题并更正评价 |
| 用户给出不同但合理的方案 | 按目标与条件判断，不强迫复现 Agent 的偏好方案 |
